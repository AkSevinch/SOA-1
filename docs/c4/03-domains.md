# Домены, распределение по сервисам и границы владения данными

## 1. Домены и их ответственность

| # | Домен | Зона ответственности | Что в домен **не** входит | Сервис-владелец |
|---|---|---|---|---|
| 1 | Идентификация | Учётные записи, роли, вход и выход, восстановление доступа, второй фактор. Для покупателя здесь же: профиль, адресная книга, избранное | Профиль продавца, товары, заказы, отзывы | Identity |
| 2 | Продавец | Профиль магазина, реквизиты, загрузка и проверка документов, статус продавца | Авторизация в системе, товары продавца | Identity |
| 3 | Каталог | Карточки товаров, категории, атрибуты, варианты, жизненный цикл товара от публикации до снятия | Цена и остаток **в момент заказа**, поисковый индекс | Catalog |
| 4 | Модерация | Проверка карточек перед публикацией, разрешение споров, блокировки, жалобы | Товары как таковые, платежи, доставка | **Catalog + Identity** |
| 5 | Корзина | Позиции покупателя, предварительный расчёт суммы, скидки на витрине | Зафиксированный заказ, реальный платёж | Cart |
| 6 | Заказ | Жизненный цикл заказа, позиции, оркестрация саги, компенсации при сбое | Деньги, отправления, уведомления | Order |
| 7 | Платежи | Авторизация, захват, возврат, ledger взаиморасчётов с продавцами | Состояние заказа, доставка | Payment |
| 8 | Выполнение | Отправления, склад, передача перевозчику, трекинг, возвраты | Деньги, уведомления, карточки товаров | Fulfillment |
| 9 | Уведомления | Шаблоны, выбор канала, защита от дублей, журнал отправок | Решение, **когда** уведомлять, и о чём | Notification |
| 10 | Поиск и персонализация | Поиск по каталогу, признаки интереса, отбор кандидатов, ранжирование, лента | Источник данных о товаре | Search |

Разница видна на домене
«Заказ»: в нём нет денег (домен 7) и нет доставки (домен 8), поэтому Order
не может ни принять платёж, ни отправить посылку сам — он только инициирует
оба шага.

### Почему модерация без отдельного сервиса

Модерация — **сквозной процесс**: модератор проверяет карточку товара, но
решает спор о заказе и блокирует аккаунт. Отдельный `Moderation Service`
собрал бы в одну базу две несвязанные модели данных — карточки товаров и
аккаунты.

Поэтому зона ответственности разделена между двумя существующими сервисами:

| Что делает модератор | Кто отвечает | Почему |
|---|---|---|
| Проверить карточку перед публикацией | **Catalog** | Работает с той же сущностью, что и продавец, в момент жизни товара |
| Одобрить или отклонить публикацию | **Catalog** | Решение меняет состояние карточки — его же хранит Catalog |
| Разрешить спор по заказу | **Identity** | Спор про пользователя и его права, данные о заказе нужны только для контекста |
| Заблокировать аккаунт | **Identity** | Аккаунт, роли и сессии принадлежат Identity |
| Вернуть товар в продажу | **Catalog** | Меняет остаток, который хранит Catalog |

Цена такого решения: модерация не изолирована в своём хранилище, и её нельзя
масштабировать отдельно. Это осознанно — объём модерации на порядки меньше
трафика каталога, а выделение отдельного сервиса потребовало бы дублирования
прав доступа к двум моделям данных.

### Почему у покупателя нет отдельного домена

| | Продавец | Покупатель |
|---|---|---|
| Что подтверждается | Документы, реквизиты, проверка статуса | Ничем: зарегистрировался — и всё |
| Где живёт | Своя сущность магазина со своей моделью | Часть общей учётной записи |
| Цикл правок | Долгий: проверка, отклонение, апелляция | Короткий: добавил адрес — и всё |
| Свой домен | Нужен | Не нужен |

Разница в наличии собственной модели данных. У продавца она есть: магазин со
статусом, документами и реквизитами не является частью аккаунта. У покупателя
её нет — он и есть учётная запись с ролью «покупатель», а адресная книга и
избранное принадлежат именно этой записи.

Поэтому данные покупателя вошли в домен «Идентификация»: профиль, адресная
книга, избранное. Отзыв — не профиль покупателя и не про учётную
запись. Это оценка товара, которая влияет на карточку, поэтому отзывы
принадлежат домену «Каталог». Покупатель не хранит свои отзывы: он пишет их
о товаре, и они живут вместе с товаром.

## 2. Распределение доменов по сервисам

### 2.1 Карта «домен → сервис»

| Домен | Identity | Catalog | Cart | Order | Payment | Fulfillment | Notification | Search |
|---|:---:|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| Идентификация | ● | | | | | | | |
| Продавец | ● | | | | | | | |
| Каталог | | ● | | | | | | |
| Модерация | ◐ | ◐ | | | | | | |
| Корзина | | | ● | | | | | |
| Заказ | | | | ● | | | | |
| Платежи | | | | | ● | | | |
| Выполнение | | | | | | ● | | |
| Уведомления | | | | | | | ● | |
| Поиск и персонализация | | | | | | | | ● |

● — домен целиком принадлежит сервису. ◐ — домен разделён между двумя
сервисами (модерация, см. выше).

**Итог: 10 доменов на 8 сервисов.** Разбиение не 1:1

| Сколько | Какие |
|---|---|
| Целиком в одном сервисе | 9 доменов — все, кроме модерации |
| Разделены между двумя | 1 домен — модерация |
| Доменов, не выделенных ни в один сервис | 0 |

API Gateway отвечает за маршрутизацию и доменом не является, Web Portal — за интерфейс

### 2.2 Логика разбиения

Правило, по которому проведены границы:

> Один сервис — одна команда, один цикл релиза, одно хранилище. Два домена
> объединяются, если они меняются вместе **и** разделяют модель данных.
> Домен выделяется отдельно, если у него собственная модель данных **или**
> его правят с другой частотой.

По этому правилу:

- **Объединены** идентификация и продавец: оба живут вокруг одной сущности
  пользователя, меняются при выдаче роли или проверке документов, то есть
  вместе. Отдельные сервисы создали бы два обращения к одному аккаунту.
- **Объединены** каталог и модерация карточек: модерация изменяет состояние
  той же карточки, её невозможно разделить без дублирования модели товара.
- **Разделены** заказ и платежи: у них разные модели (жизненный цикл против
  денежных транзакций), разные правовые требования и разный риск — компрометация
  платёжного сервиса не должна давать доступ к заказам.
- **Разделены** заказ и выполнение: склад и доставка живут своей жизнью,
  сменой перевозчика интересуется операционный контур, а не продавец.
- **Отдельно** Notification: у него единственная входящая связь — шина
  событий, и он ничего не знает о заказах и товарах. Ему не нужна общая
  модель данных, только события.

### 2.3 Почему не 1:1

Если бы каждый домен обязательно получал свой сервис, пришлось бы разделить, например, "Идентификацию" и "Продавца" на два разных сервиса — хотя оба крутятся вокруг одной и той же сущности (пользователь), меняются вместе и одной командой. Разделять их только ради "чистоты схемы" означало бы:

два сервиса, которые постоянно дёргают друг друга по сети за одними и теми же данными,
два деплоя там, где на деле всегда нужен один,
лишнюю инфраструктуру (своя база, свой контейнер, свой мониторинг) без реальной пользы.

## 3. Границы владения данными

### 3.1 Кто что хранит

| Сервис | Хранит | Отвечает | Кому **нельзя** давать доступ |
|---|---|---|---|
| Identity | `identity_db`: пользователи, роли, профиль продавца, документы, адресная книга, избранное | Регистрация, вход, роли, профиль покупателя и продавца | Всем, кроме Order, Cart и Notification — и только на чтение по запросу |
| Catalog | `catalog_db`: карточки, категории, атрибуты, ссылки на медиа, отзывы и оценки | Жизненный цикл товара, модерация карточек и отзывов | Поисковому индексу — он наполняется из событий, а не из чтения таблицы |
| Cart | `cart_db`: корзины и позиции | Состав корзины, предварительный расчёт | Поиску — только после превращения корзины в заказ |
| Order | `order_db`: заказы, позиции, состояние саги, журнал статусов | Жизненный цикл заказа, компенсации | Платежам и доставке — они получают данные по ссылке, не читают таблицу |
| Payment | `payment_db`: платежи, транзакции, ledger выплат | Деньги, взаиморасчёты с продавцами | Ни одному сервису: наружу уходят только итоговые статусы |
| Fulfillment | `fulfillment_db`: отправления, трекинг, условия возврата | Склад, отправления, возвраты | Поиску ленты — статус доставки не влияет на выдачу товара |
| Notification | `notification_db`: шаблоны, журнал отправок, признаки прочитанного | Как уведомлять, куда, без дублей | Никому, кроме самому себе и шины |
| Search | `search_db`: признаки интереса, история показов и кликов | Поиск, лента, ранжирование | Каталогу — признаки выводятся из событий, чтения `catalog_db` не происходит |

### 3.2 Разделяемых баз данных нет

Каждая из восьми баз принадлежит ровно одному сервису, и это видно на
[контейнерной диаграмме](02-container.md): у каждой базы ровно одно входящее
ребро — от своего владельца.

| Проверка | Результат |
|---|---|
| Всего баз | 8 |
| Баз с одним владельцем | 8 из 8 |
| Баз, в которые пишет чужой сервис | 0 |
| Прямых SQL-запросов к чужой базе | 0: у сервисов физически разные подключения и нет общих учётных данных |

Ключевой момент: данные **передаются**, а не разделяются. Когда Order нужны
данные о товаре, он вызывает Catalog по HTTP. Когда Search нужны новые
товары, он читает событие из шины. Ни один сервис не делает `SELECT` к
чужой базе — это делает невозможным даже случайное соединение.

Особый случай — `search_db`. Это персональные данные пользователя (история
просмотров), но они хранятся **внутри** Search, а не в общей базе. Поиск
узнаёт, кто смотрит ленту, вызовом Identity по gRPC, и ни разу не читает
таблицы пользователей. Поэтому персональные данные не размазаны по всей
системе, а изолированы там, где они используются.

### 3.3 Взаимодействия: кто с кем и как

Всего 19 связей, у каждой указана технология и синхронность.

| Тип | Сколько | Когда применяется |
|---|---|---|
| `sync` | 12 | Вызывающий **ждёт ответа**, чтобы продолжить решение: нельзя отдать заказ, не зная цены |
| `async` | 7 | Шаг **не держит критический путь**: индекс и уведомление могут подождать |

Разделение видно по конкретному примеру. Оформление заказа:

```
Order → Cart      sync   списать корзину: без этого заказ не существует
Order → Catalog   sync   проверить цену: нельзя принять неверную цену
Order → Identity  sync   участники заказа: нужен состав
Order → Payment   sync   сага ждёт захвата: без денег не создаём отправление
   ↓ Order → шина  async  всё остальное уходит фоном
```

Четыре синхронных шага — это критический путь, покупатель ждёт подтверждения.
А уведомление о заказе, обновление индекса и сообщение продавцу о деньгах
уходят в шину и обрабатываются позже: если Notification упал, заказ всё равно
оформлен. если шаг можно выполнить позже без потери смысла — он
асинхронный. Всё, что меняет состояние бизнес-сущности, о которой покупатель
ждет ответа, — синхронное.

Исключение, которое стоит отметить: `Order → Payment` синхронен, хотя платёж
формально «после» заказа. Это сделано намеренно — сага должна знать, что
захват прошёл, прежде чем создавать отправление. Альтернатива (создать
отправление оптимистично и откатить при отказе платежа) порождает
«висящие» отправления, что хуже для склада.
